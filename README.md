# QUERYBUILDER

A fluent, chainable SQL builder for `_LindseyEngine`. It assembles a **parameterized query plan**
and never touches the database itself — the engine executes it. Values are always bound as named
parameters (safe against injection); identifiers (field names, raw SQL, joins) are not — never
pass untrusted input into those positions.

```php
$engine = new _LindseyEngine('personalia_member', $jsonData);

$engine->get(   (new QUERYBUILDER())->filter('state', 'active', '=') );          // SELECT
$engine->set(   (new QUERYBUILDER())->filter('id', 5, '=')->data(['state'=>'closed']) ); // UPDATE
$engine->set(   (new QUERYBUILDER())->data(['full_name'=>'Budi']) );             // INSERT (no filter)
$engine->delete((new QUERYBUILDER())->filter('id', [1,2,3], 'IN') );             // DELETE
```

## How it works

`QUERYBUILDER` is **pure** — it only builds SQL. You construct it, chain methods, and hand it to
the engine, which detects it and runs the execution:

1. the engine calls `setObjectName()` + `setConfig()` on the builder,
2. resolves ownership (and, for reads, global pagination),
3. calls the pure plan builder (`build()` / `buildUpdate()` / `buildDelete()`),
4. prepares and executes the statement(s).

The same WHERE engine (`filter`, `or_filter`, `where_group`, `IN`/`BETWEEN`/`LIKE`, raw filters)
is reused across **get / set / delete**.

## Cross-cutting rules

- **Ownership** — fields listed in the model's `ownership` config are auto-injected from
  `$GLOBALS['ownership_data']` (the request header, validated in Bootloader) and **AND-ed at the
  outermost level**, so a top-level `OR` can never widen results past the ownership scope.
    - A channel-level `->ownership_data('field', $value)` **pin wins** over the header (trusted,
      not re-validated against the binding — never pin raw client input).
    - Reads are **lenient** (missing value → skip); writes are **strict** (missing value → throw).
    - A field passed to `ownership_data()` that isn't a configured ownership field **throws**.
    - **Only via `ownership_data()`** — an ownership field used in `filter()` (structured or raw)
      **throws** across get/update/delete; it must never sit inside a user `OR` group.
    - **Immutable** — an ownership field passed to `set()`'s `data()` **throws**; ownership is set
      once at creation (from a pin or the header), never reassigned by a normal write.
    - **Multiple ownership fields** — call `ownership_data()` once per field; each is AND-ed
      separately. Same field twice → last value wins.
- **Writes never touch the whole table by accident** — `set($qb)` with no filter is an INSERT
  (not a mass UPDATE); `delete($qb)` with no filter is rejected.
- **Write guards** — SELECT-only clauses (`fields`, `join`, `fk`, `children`, `properties`,
  `group_by`, `having`, aggregates, `distinct`, `sort`, pagination) are rejected on `set`/`delete`.

## Implementation

All in `Library/engine/_LindseyEngine.php` (class `QUERYBUILDER` + the engine's
`get()`/`set()`/`delete()`). Note: `Library/` is generated by `setup.php` from the fetched
config artefact and is gitignored — engine changes must also land in the upstream artefact to
persist. These docs live in the repo and are tracked normally.

# Authentication

Two independent, composable layers on every request through `Bootloader.php`:

- **`X-API-Key`** (`api_tokens` table, auth DB) — which app/channel a caller may hit at all
  (`scopes`, `channel_list`). Unrelated to membership; unchanged by anything below.
- **`session-token`** (`membership`/`membership_session` tables, auth DB) — which _member_ is
  acting, and what ownership values they're allowed to touch. **Required on every request**
  through `Bootloader.php`, regardless of whether the target object even declares an `ownership`
  field.

Full design and rationale: [docs/2026-07-23-membership-ownership-auth.md](docs/2026-07-23-membership-ownership-auth.md).

## Getting a session

`POST /auth/login` (or `/auth/login.php`), JSON body:

```json
{ "member_identifier": "someone@example.com", "password": "..." }
```

Requires a `membership` row already provisioned for that `member_identifier` (Dashboard →
Membership → Add Membership) — a successful credential check alone isn't enough, admin
provisioning is a separate, required step. Response:

```json
{ "session_token": "…", "expires_at": "2026-07-23 12:00:00" }
```

Hard 2-hour expiry, no refresh — call `/auth/login` again once expired. Only one session is active
per member at a time; logging in again elsewhere invalidates the previous session.

`POST /auth/logout` with header `session_token: <token>` revokes it immediately.

> **Current limitation**: credential verification (`auth/_user_service_client.php`) is a dummy
> stub — any non-empty password succeeds for a provisioned `member_identifier`. Real user-services
> integration is a single, isolated swap point, not yet wired up. Treat this as tech debt, not a
> finished auth flow, until that lands.

## Using a session

Every subsequent request (`index.php`'s API path, i.e. everything under `/channels/<name>/...`)
must include the header:

```
session_token: <token from /auth/login>
```

Missing or expired → `401`. `Bootloader.php` resolves the token to the member's ownership
whitelist (`membership_ownership_value`) and populates `$GLOBALS['ownership_data']` with it before
the channel endpoint runs — see the QUERYBUILDER ownership docs above for how `get`/`_get`/`set`/
`_set`/`delete`/`_delete` each consume that whitelist.
